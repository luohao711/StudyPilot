\section*{1. 实验目的}

\begin{itemize}
  \item 编写并运行模型调用代码，掌握输入组织、结构化输出校验和调用失败处理。
  \item 完成资料切分、检索、上下文组织、回答生成与来源引用，理解RAG各环节的作用。
  \item 使用固定问题集对比直接调用模型与使用RAG的回答，分析效果与局限。
\end{itemize}

\section*{2. 实验内容}

\subsection*{2.1 LLM调用与输出格式}

\begin{itemize}
  \item 选择一个知识问答任务，说明用户问题、输入内容和结果用途；结合个人软件时，注明对应个人软件的用户故事。
  \item 编写并运行云端模型调用代码，记录模型名称、调用方式、配置和主要参数，展示完整输入与返回结果，并测试至少一种连接失败、接口不可用或超时情况。
  \item 运行至少3组输入，包含正常问题、缺少必要信息的问题和超出任务范围的问题，记录期望与实际结果。缺少信息时提示补充或追问，超出范围时按任务要求提示无法处理。
\end{itemize}

\subsection*{2.2 Prompt与上下文组织}

\begin{itemize}
  \item 编写可重复使用的Prompt模板，区分任务要求和用户问题，明确回答格式及信息不足时的处理。完成RAG后加入检索资料与来源，多轮对话按需加入历史消息，并展示一份实际发送给模型的完整输入。
  \item 根据测试结果修改至少一次Prompt，记录原版本、修改原因、修改内容和结果变化；结论限于本次样例，未改善或出现退步也应记录。
  \item 检查输入中是否存在无关或重复信息，按需精简并记录检查结果；有删减时比较长度与回答变化。选择和组织模型输入信息称为上下文工程；长度可用字符数或Token数。
\end{itemize}

\subsection*{2.3 知识库与切分策略}

\begin{itemize}
  \item 根据个人软件选择少量、来源明确的资料作为知识库；记录数量、格式、使用权限和隐私处理方式，清理乱码、重复及无关内容，不得向外部模型发送敏感数据。
  \item 按段落、标题或长度切分文本，说明片段大小、相邻片段是否重叠以及资料更新方法。
  \item 抽查至少3个片段，展示内容与元数据，检查关键语句是否完整、来源是否对应原资料。发现问题时调整切分方式并重新检查。
\end{itemize}

\subsection*{2.4 检索与RAG最小链路}

\begin{itemize}
  \item 实现关键词检索、向量检索或二者结合的方法，并说明选择理由。关键词检索按词语匹配；使用向量检索时，用同一嵌入模型分别将资料片段和用户问题转为数值向量，再比较相似程度，记录模型名称与比较方法。
  \item 展示一次查询、按相关性排序的前k个片段（Top-k）及排序依据，说明k的取值。返回片段不代表资料相关，应说明判断方法，如关键词匹配规则、经样例检查的相似度阈值或模型判断；无结果或资料不相关时，返回资料不足提示。
  \item 将检索片段与来源编号加入上下文，生成带出处的回答，检查引用是否对应原片段、是否支持回答；资料不足时明确提示，不编造答案或引用。
  \item 完成“问题输入—检索—上下文组织—模型调用—回答返回”的流程，保存检索片段、实际上下文和最终回答。
\end{itemize}

\subsection*{2.5 对比测试与质量分析}

\begin{itemize}
  \item 建立5—8个固定问题及判断规则，包含单片段可回答、多片段综合，以及资料无答案或含义不清的情况，写明处理方式，供后续实验重复使用。
  \item 两组使用相同问题、模型、主要参数和基本输出格式：直接模型组不提供检索资料，RAG组增加资料及依据资料回答、引用来源的要求。说明两组提示词的差异；各次测试使用独立上下文，避免前一次结果影响后一次测试。
  \item 用统一表格记录两组回答和人工判断，比较正确性、要点遗漏和无依据内容，另检查RAG组的引用可靠性。资料无答案时，区分模型凭已有知识回答与资料能够支持回答。
  \item 记录从输入到返回结果的耗时，以及可获取的Token数或调用次数；收费接口补充实际或估算费用。
\end{itemize}

\subsection*{2.6 模块调用与后续使用}

\begin{itemize}
  \item 将检索和回答生成整理为可调用的模块，说明依赖、调用方式、输入、输出及失败返回，并提供知识库准备方法。
  \item 提供页面、接口或命令行入口，演示从输入问题到显示回答与出处的完整过程。
  \item 说明个人软件是否继续使用RAG及理由，需要时指出拟接入的功能；列出当前局限和下一步改进计划。
\end{itemize}

\subsection*{3.1 任务与模型调用}

问答任务是“StudyPilot 资料问答”：用户用自然语言问项目或课程学习相关的问题，系统从本人编写的项目文档里检索资料，给出带出处的回答。结果用途是复习和查资料，不直接写入学习计划。对应的用户故事是实验2里的“作为本科生，我希望把课程要求转换成可修改的学习计划，以便按时完成任务并了解自己的薄弱知识点”，本实验补充的是其中的查资料环节。

模型调用代码在 \texttt{backend/app/service/llm\_client.py}，用 httpx 调用 DeepSeek 的 Chat Completions 接口，密钥只从环境变量 \texttt{DEEPSEEK\_API\_KEY} 读取，不写进代码和日志。请求参数使用 \texttt{deepseek-chat}，实际返回的 \texttt{model} 字段以接口响应为准。

样例检查发现过一次检索失败：问“系统数据库里保存了哪些数据？它们之间是什么关系？”时，前 3 个片段都是实验3的设计说明，没有检索到数据模型的内容，回答只能给出资料不足。原因是问题和资料用词不一致（问“数据库、数据”，资料里写的是“表、字段、主键”），而且正文里的通用词太多。加入标题加权和同义词扩展后，数据模型说明的“表之间的关联”片段排到第 1，回答也正确了。

RAG 链路为：问题输入 → 检索 Top-k 片段 → 按“[编号] 来源/章节/正文”组织上下文 → 调用模型并校验 JSON → 检查引用编号并返回回答。引用核对会检查编号是否在检索结果范围内，并计算被引用片段与回答的词语重合度，低于 0.12 标记为需要人工复核，编号越界直接判为不可靠。3.5 的对比测试中 RAG 组共引用 13 处：12 处重合度不低于 0.12，1 处（Q6 的 [3]，S5-001）为 0.098，需要人工复核；逐条回看片段，发现它只是数据模型说明的来源元数据，不能直接支持表关系，属于弱引用。没有出现编号越界。

资料不足分两种处理：检索完全没有结果时（如“项目开发一共花了多少钱”）直接返回资料不足，不调用模型；检索到了片段但资料回答不了时（如“用的是哪种知识追踪算法”），把 sufficient 置为 false，并在回答里说明缺少什么信息。对比测试的完整记录保存在 \texttt{backend/tests/data/compare\_result.json}，包含问题、检索片段、实际上下文、回答、引用检查、耗时和 Token。

本次共执行 16 次测试运行（Q8 的 RAG 组因检索无结果未调用模型，实际模型调用 15 次），合计 7316 tokens，按输入 2 元/百万、输出 8 元/百万估算约 0.0224 元，总用时 22.0 秒。直接组 8 次共 1687 tokens、约 0.00685 元；RAG 组 7 次调用共 5629 tokens、约 0.01553 元。RAG 的 tokens 约为直接组的 3.3 倍（输入 tokens 约 4.4 倍），费用约为 2.3 倍；耗时两组接近（直接组合计 12.1 秒、RAG 组合计 9.9 秒），本次网络波动较大，不能据此认为 RAG 一定更快或更慢。

人工检查回答内容，主要差别有四点。第一是正确性：直接模型在项目专属问题上给出了看似合理但和项目不符的内容。Q1 把架构说成“表示层、应用层、领域层、基础设施层”，项目实际是“表现层、业务层、AI服务层、数据层”；Q2 说“系统根据练习/测验结果自动更新掌握度”，实际是用户填写或确认后更新；Q3 提到规则/模板但没有手工调整入口；Q4 编造了“多用户协作/社交、复杂推荐算法、移动端 App、第三方日历、知识图谱可视化、自动出题与批改”等 MVP 排除项；其中只有“社交、知识图谱”等少数与资料重合，其余在资料中没有依据。RAG 组的回答都能在原片段里找到对应句子。第二是资料无答案时的处理：直接模型 Q7 没有编造具体算法，而是列出 BKT、DKT、IRT 等候选并建议查看设计文档，Q8 以超出范围为由拒绝；RAG 组 Q7 明确说明资料不足并指出缺少算法说明，Q8 说明知识库没有费用信息且未调用模型，两题都没有编造。第三是引用可靠性：RAG 组 13 处引用中 12 处通过重合度阈值，1 处弱引用已人工标注，没有编号越界；但“能引用”不等于“引用足以支持结论”，Q6 的弱引用就是例子。第四是自动要点打分的局限：Q6 直接组按关键词判为 3/3，但它把掌握度说成“掌握度记录”、把任务说成关联计划，和实际数据模型有出入，说明关键词命中只能作为初筛，最终还要人工判断。

也有 RAG 答得不够好的地方：Q1 已经正确说出四层名称，却在末尾补“各层详细分工资料不足”，被程序标成“资料不足声明=是”，看起来像没有回答完整；Q7 只检索到 1 个片段，答案信息量偏少；Q1 和 3.1 的掌握度问题都把 README 的“资料问答（RAG）”小节排进前几名，关键词分数高但内容与问题无关，说明检索排序仍有噪声。结论是：RAG 的作用是把回答限制在资料范围内、并提供可核对的出处，不能代替人工判断内容是否准确；本次样例中 RAG 在项目专属事实和“资料不足”处理上明显更好，直接模型在措辞自然度和通用知识上不差，但容易把通用知识当成项目事实。

\section*{4. 实验小结}

本次完成了 StudyPilot 的资料问答功能：用 DeepSeek 的 chat completions 接口做模型调用，把 5 篇项目文档转成 77 个片段的知识库，用 BM25 关键词检索做检索，再让模型依据检索到的片段生成带出处的回答，前端加了一个“资料问答”页面，命令行和接口也都能调用。

过程中主要做了四件事。第一是 Prompt 改了两次：初版没有格式要求，回答发散、使用 Markdown 列表且引用格式不受约束；第二版要求只依据资料、限制长度并输出 JSON，引用可以逐条核对；测试三组输入时又发现“帮我设置考试目标”这类缺少参数的操作请求会被当成普通问题回答，于是加了追问规则。对比 v2 和 v3 可见 v3 会先说明缺少参数、再列需要补充的信息，但回答里仍带出字段名和接口，追问还不够简洁。第二是知识库重建：抽查时问“数据库保存了哪些数据”，旧版只命中实验3的设计说明；补一份数据模型说明后回答正确；本次重跑还把 README 的资料问答说明纳入知识库，片段数从 74 变为 77，说明资料更新后必须重建索引。第三是检索调整：加入标题加权和同义词扩展后，同一个问题的正确片段从检索不到变成排在第 1。第四是上下文工程：Top-k=6 时上下文 1577 字、包含 LaTeX 编译命令等无关内容和重复命令，按分数精简到 657 字（减少 58\%），prompt tokens 从 1080 降到 541，回答和引用没有变化；但按分数精简不能去掉所有噪声，README 的高分无关片段仍会保留。

对比测试用 8 个固定问题跑了 16 次测试（实际 15 次模型调用），共 7316 tokens、约 0.0224 元、22.0 秒。直接模型在项目专属问题上会给出看似合理但不符实际的内容（架构分层名称、自动更新掌握度、编造 MVP 排除项），有检索结果且给出引用的 RAG 回答都能对应到原片段；Q8 未调用模型、没有引用，两个资料无答案的问题也都明确说明资料不足。RAG 也不是没有问题：Q1 已经答对却补充“资料不足”，Q7 检索片段偏少，README 的 RAG 说明会排进前几名，引用核对只能看词语重合度（本次有 1 处弱引用）。局限是关键词检索依赖用词、知识库范围有限、RAG 的 tokens 和费用约为直接模型的 3.3 倍和 2.3 倍；后续用固定的 8 个问题做回归测试，补充资料并改进过滤，再考虑关键词与向量检索结合。
